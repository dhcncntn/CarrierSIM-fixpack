# Фикс-пак CarrierSIM: AirTraffic «2 из 3», ложные «Books state differs», блокировки восстановления

Патч к `carrier.py` (CarrierSIM, техника AirLift). Устраняет причины, по которым
на iOS 27 установка падает на шаге экспорта каталога, восстановление Books
даёт ложные сбои, а после любой ошибки скрипт блокируется командой
«Сначала выполните --recover».

> **Ничего не понимаете в терминалах?** Вставьте в любой чат-бот (ChatGPT,
> Claude, DeepSeek…) два файла из этой папки — `AI-INSTRUCTIONS.md` и этот
> README — плюс текст вашей ошибки, и бот просто проведёт вас по шагам.

## Что входит в фикс-пак

1. **Чистка OutstandingAssets** (`clean_outstanding`): зависшие path-подобные
   строки в `Books/Sync/Database/OutstandingAssets_*.sqlite` на iPhone удаляются
   перед каждой операцией и после неё. Это причина «AirTraffic не подтвердил
   нужные объекты (подтверждено 2 из 3)».
2. **Летучие узлы Books**: sqlite-базы, `-shm`/`-wal` sidecar'ы и `.lock`-файлы
   переписываются iOS на лету — их содержимое больше не сравнивается побайтно
   (только наличие и тип). Это причина большинства ложных
   «Books state differs; backups retained».
3. **Примирение с повторами**: восстановление Books выполняется до трёх
   проходов, если iOS не успел затихнуть между записью и проверкой.
4. **Чтение с повторами**: «Remote file changed during read» больше не фатально —
   дерево Books перечитывается до трёх раз.
5. **Безопасное восстановление**: файлы, которые могут быть пользовательским
   контентом (всё не-летучее вне `Sync/`), при восстановлении не удаляются —
   книга, добавленная во время операции, не пропадёт.
6. **Восстановление без тупиков**: `--recover AUTO` чинит все незавершённые
   этапы подряд (раньше — падение на втором), автовосстановление после обрыва
   связи обрабатывает несколько этапов, а `--recover <путь>` принимается, если
   путь входит в список незавершённых (раньше требовалось совпадение со всеми
   сразу — взаимная блокировка двух журналов нельзя было разорвать штатно).
7. **Windows: поиск библиотек Apple** — расширенные стандартные пути, авто-поиск папок Apple/iTunes в программных каталогах и подробная диагностика с готовой командой, если CoreFoundation.dll/AirTrafficHost.dll не найдены (частая беда Microsoft Store-версии iTunes).

## Симптомы

Любой из этих признаков — ваша история:

- Установка останавливается с ошибкой
  `AirTraffic не подтвердил нужные объекты (подтверждено 2 из 3)` — обычно на
  шаге «Сохраняю исходные настройки».
- Та же ошибка повторяется **каждый** запуск, включая `--recover` и автовосстановление.
- После сбоев накапливаются незавершённые этапы, блокирующие меню, а в логах
  хоста (`host.jsonl`) видно:
  `"missing": ["../../../Library/Carrier Bundles/iPhone"]` — из манифеста
  стабильно выпадает один и тот же объект (экспорт каталога).

## Причина

iOS хранит состояние Book-ассетов синхронизации AirTraffic в базе
`/var/mobile/Media/Books/Sync/Database/OutstandingAssets_*.sqlite`
(таблицы `ZBCOUTSTANDINGASSET` / `ZBCINSTALLEDASSET`, колонка `ZPERSISTENTID`).

Ассет-экспортёр каталога операторов всегда объявляется с одним и тем же
Persistent ID — путём `../../../Library/Carrier Bundles/iPhone`. Если сессия
синхронизации прервалась (сбой связи, таймаут, аварийное завершение), строка
этого ассета остаётся в базе, и iOS на **каждом** следующем запуске считает
ассет «уже в работе» и молча выбрасывает его из манифеста. Дальше скрипт
справедливо отказывается продолжать без подтверждения — и так по кругу.
Наблюдение на iOS 27: счётчик изменений застрявшей строки переваливал за 50.

`--recover` тут не помогает по построению: восстановление само пользуется тем же
механизмом и наследует ту же застрявшую строку.

## Что делает патч

Добавляет в `carrier.py` функцию `clean_outstanding(afc)` и вызывает её дважды
внутри `transfer()`:

1. **перед** каждой операцией (после снимка Books) — само-лечение: любой прошлый
   сбой отчищается до staging;
2. **после** восстановления Books в конце операции — устройство остаётся чистым.

Логика чистки:

- обрабатываются **все** базы `OutstandingAssets_*.sqlite` — числовой суффикс
  меняется между версиями iOS, поэтому имя не захардкожено;
- удаляются только строки, у которых `ZPERSISTENTID` — относительный путь
  (`LIKE '../%'`), в обеих таблицах. Так помечают ассеты любые инструменты на
  технике AirLift; настоящие книги (hex/UUID идентификаторы) не страдают никогда;
- корректно обходятся `-wal`/`-shm`: подтягиваются перед правкой, после записи
  удалённые — устройство не увидит рассинхронизированный журнал;
- чистка best-effort: любая ошибка (нет базы, нет доступа) не роняет операцию, а
  только печатает предупреждение.

Фактически после патча телефон после каждого прогона не содержит path-подобных
записей синхронизации, и один и тот же сбой больше не воспроизводится по кругу.

## Как применить

Один способ для любой ОС — самоприменяющийся установщик, нужен только Python
3.11+ (он и так требуется самому CarrierSIM):

```bash
cd CarrierSIM          # в папку, где лежат carrier.py и apply-fix.py
python apply-fix.py    # macOS / Windows / Linux — одинаково
```

Установщик сам: проверит совместимость версии `carrier.py`, сделает резервную
копию (`carrier.py.bak-airtrafficfix`), вставит фикс, проверит синтаксис.
Полезные режимы:

```bash
python apply-fix.py --check    # применён ли фикс уже
python apply-fix.py --revert   # вернуть carrier.py из резервной копии
```

Если хочется по-старому — дифф тоже работает (macOS/Linux: `patch -p0 <
airtraffic-outstanding-fix.patch`; Windows: то же самое из Git Bash или WSL).

### Ручное применение (для любой ОС)

Установщик и дифф написаны против `carrier.py` от 2026-09-28 (62 958 байт,
версия с автовосстановлением). Если контекстные строки не сойдутся с вашей
версией, можно применить вручную:

1. Добавить функцию `clean_outstanding` (см. патч) перед `async def transfer(...)`.
2. Внутри `transfer()` сразу после `books, books_existed = await books_snapshot(afc, run)`
   вызвать `await clean_outstanding(afc)`.
3. В `finally`-блоке после успешного `restore_books(...)` (перед финальным
   `save_json`) вызвать `await clean_outstanding(afc)` ещё раз.

## Как проверить

```bash
# контрольное чтение каталога (ничего не записывает):
python3 carrier.py --recover AUTO   # или штатный запуск
# в host.jsonl прогона манифест должен собрать все 3 объекта:
grep manifest-diagnostic runs/<прогон>/host.jsonl
# ожидание: "book_record_count": 3 ... "missing": []
```

## Проверено

- iPhone 17 Pro Max, iOS 27.0.1 (24A446), две SIM: до патча — 4 сбоя подряд
  «2 из 3»; после патча чтение каталога и полная установка прошли с первого
  раза, выбор `Vodafone_hu.bundle` подтверждён по журналу CommCenter для обеих SIM.
- После прогона таблица OutstandingAssets пуста, телефон не накапливает мусор.

## Автору

Один абзац сути: AirTraffic-ассеты дедуплицируются по `ZPERSISTENTID` в
OutstandingAssets; прерванная сессия оставляет строку, и ассет перестаёт
попадать в AssetManifest навсегда. Предлагается чистить path-like строки
(`ZPERSISTENTID LIKE '../%'`) до staging и после restore_books.
Контакт по фиксу: владелец этого экземпляра CarrierSIM (см. тред 4PDA, topic 1055886).
